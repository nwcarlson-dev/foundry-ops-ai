# The data is synthetic. Here is exactly what is in it.

No real LeClaire Manufacturing data was used, and none was available to me. Every
row in this database is generated by [`scripts/generate.ts`](../scripts/generate.ts)
from a fixed seed.

Saying so up front is deliberate. A demo that quietly implies it is running on
someone's production data is worse than useless to a foundry — the first person
who checks a number against reality stops trusting the whole thing. What follows
is the complete disclosure: how the data is shaped, what is deliberately wrong
with it, and what findings are planted in it.

The realism claim is narrow and specific: **the structure, vocabulary, and
failure modes are real; the numbers are invented.** Table and column names follow
Epicor job-cost conventions. The scrap reason codes are the real vocabulary, and
each defect is attributed to a cause that actually produces it. The reconciliation
problems are the ones that occur when four systems grow up separately.

## Reproducibility

```bash
npm run seed      # drops, recreates, regenerates — identical output every time
npm run verify    # 37 assertions: every planted signal present and detectable
```

`npm run verify` is not decoration. The failure mode that would actually damage
this project is a copilot confidently reporting a number that is wrong, and if a
signal silently stops generating, every surface built on top of it lies. It has
already earned its keep: it caught a downtime check that compared absolute hours
across mismatched window lengths, and the generator's own guard caught a seed
where no job qualified for the flagship question.

Seed constant: `20260729`. Dataset window: **2025-01-29 → 2026-07-29** (18 months).
The dataset's "today" is pinned to **2026-07-29** so results are stable and the
copilot's sense of *now* does not drift. That date is stated in the system prompt.

## Why four schemas instead of one database

The job posting names Epicor, Thrive, Ignition/PaperlessLog, and monday.com, and
asks for "a unified AI layer that can reason across them together." Modeling that
as one tidy warehouse would dodge the actual problem. So the four sources are
four Postgres schemas that **share no keys**, each carrying its real system's
conventions:

| Schema | Real system | Keys on | Critically, does **not** know |
|---|---|---|---|
| `epicor` | ERP job cost | `job_num` `J-104829`, `part_num` `4471-BRKT` | anything about heats or machine tags |
| `thrive` | Melt deck & quality | `heat_num` `H26-0412`, `pattern_code` `PTN-0113` | Epicor job or part numbers |
| `ignition` | SCADA historian | `tag_path` + timestamp | any part, job, or heat identifier |
| `monday` | Customer board | numeric `item_id` | anything — the job link is free text |

The `xref` schema is the bridge, and it is the substance of the project. Three
bridges, each with a different failure mode:

- **`xref.part_pattern`** — Epicor part ↔ Thrive pattern. A hand-maintained
  mapping table, because no system owns both namespaces.
- **`xref.wc_tag`** — Epicor work center ↔ Ignition tag prefix. Since the
  historian has no production identifiers, joining to a job additionally requires
  a **time window**, derived in `xref.job_window` from the job's labor records.
- **`xref.normalize_job_ref()`** — a SQL function that recovers a canonical job
  number from whatever a human typed into monday.com's `Job #` column.

### The bridges are deliberately imperfect

Real reconciliation is never clean, and a layer reporting a 100% match rate is one
nobody in a plant would believe. So:

| Deliberate defect | Where it shows up |
|---|---|
| 2 parts (`4590-ADPT`, `7201-TRIM`) were never mapped to a Thrive pattern | `xref.unmatched` |
| `PTN-0207` serves **two** part numbers (`3320-HSG`, `3321-HSG`) — same tooling, two customer part numbers | `xref.part_pattern` |
| `PTN-0455` was poured on the melt deck but the ERP never knew about it | `xref.unmatched` |
| `Utilities/AirComp2/PressurePSI` is a real historian tag mapped to no work center | `xref.unmatched` |
| Some monday `Job #` cells are blank or still say `TBD` | `xref.unmatched` |
| 4 monday items reference job numbers that do not exist in Epicor | `xref.unmatched` |

**`xref.unmatched` is shipped on purpose and the copilot is instructed to cite
it.** An answer that says "3 monday items could not be matched to a job" is more
trustworthy than one that silently under-reports.

### The `Job #` column really is that bad

Four formats appear in the data, plus blanks and a stale placeholder:

| Raw value | `normalize_job_ref()` |
|---|---|
| `J-104829` | `J-104829` |
| `J104829` | `J-104829` |
| `104829` | `J-104829` |
| `Job 104829` | `J-104829` |
| `` (blank) | `NULL` |
| `TBD` | `NULL` |

## The five planted signals

Each is a real foundry failure mode. **Each is deliberately split across source
systems** so it cannot be found inside any single schema — that constraint is
enforced by the generator and asserted by `npm run verify`.

### 1. Gas porosity from a drifting degas cycle — *needs all four sources*

This is the flagship. Over the **final 8 weeks**, scrap coded `GASPOR` climbs
sharply on castings poured from furnace 3. The cause is not in Epicor.

| Source | What it contributes |
|---|---|
| `epicor` | `GASPOR` share of scrap on the bracket family rises from **~6% to ~59%** |
| `thrive` | `degas_minutes` on `FURN-3` drifts **12.0 → ~6.0 min** over the same weeks |
| `thrive` | `rpt_density` falls with degas time — Pearson **r = 0.91**, the physical mechanism rather than a coincidence |
| `ignition` | `Melt/Furnace3/DegasMinutes` independently records the same decay |
| `monday` | Two `Stuck` Deere expedites sit on affected jobs, one promised the day after the dataset's "today" |

The narrative: nobody changed a setpoint. The degas cycle timer drifted, less
hydrogen came out of the melt, and it surfaced two operations downstream as
porosity. Epicor can tell you *that* scrap went up. Only the join tells you
*why*, and only the fourth source tells you a customer is about to be affected.

**It is a furnace problem, not a part problem.** Under-degassed metal leaves
dissolved hydrogen in *everything* poured from that furnace, so susceptibility is
graded by geometry rather than restricted to one part number:

| Part group | GASPOR share, last 6 weeks |
|---|---|
| Heavy-section sand brackets (`4471-BRKT`, `4482-BRKT`) | ~59–66% |
| Other A356 sand castings | ~44% |
| Thin-wall A356 permanent mold | ~20–29% |
| Anything not on furnace 3 (319, 535) | unaffected |

That grading is what makes the finding worth surfacing: a copilot that says "it's
the bracket" is less useful than one that says "it's furnace 3, worst on the
heavy sections."

Two modeling choices matter here, and both are deliberate:

- **Porosity scrap is *additive*, not relabeled.** The generator adds porosity
  losses on top of baseline process scrap rather than recoloring a slice of it.
  That is the physically correct story — the hydrogen is already in the metal —
  and it is why the weekly trend climbs steadily instead of sloshing around as a
  share of a small random pool.
- **Furnace identity is decided once per job** and drives the Epicor melt work
  center, the Thrive heat record, and the Ignition tag tree together, so
  `MELT-F3` ↔ `FURN-3` ↔ `Melt/Furnace3/*` all describe the same physical
  furnace. An earlier version rolled these independently and the two systems
  reported 12.2 and 9.2 minutes for the same job — which would have discredited
  exactly the corroboration this signal rests on.

Corroboration across Thrive and Ignition is the point: a drift visible in two
independent systems is a finding; the same drift in one system is an artifact.

**The two expedited jobs are planted deliberately.** The flagship question needs a
job that is simultaneously mid-routing, carrying porosity scrap, and due soon. At
~11% part share and ~2.3 job releases a day, only a job released in the last two
or three days is still mid-routing, so leaving it to chance would break the demo
on some seeds. `scripts/generate.ts` releases them on purpose and **throws if no
qualifying job exists** rather than seeding a dataset the flagship question falls
flat on.

### 2. Second-shift efficiency on mold line 2

Starting around **day 380**, a new-hire cohort (`E-2011`, `E-2014`, `E-2019`,
`E-2026`) joins second shift on `MOLD-L2`. Actual-to-standard hours degrade by
roughly 22% at the peak, then **recover gradually** as they learn. First shift on
the same work center is unaffected — which is what makes it a staffing story
rather than an equipment story.

*Lives in:* `epicor.labor_dtl` (shift, employee) + `epicor.job_oper` (est vs act).

### 3. The pump-housing standard is wrong

`3320-HSG` and `3321-HSG` run ~25% over `est_prod_hrs` on the **CLEAN** operation,
consistently, across every job and **every operator**. That last part is the
tell: an overrun spread across the whole crew is a bad standard, not a
performance problem. The estimate was set once and never revised.

*Lives in:* `epicor.job_oper` — but distinguishing it from signal 2 requires
`epicor.labor_dtl` to show the overrun is not operator-specific.

### 4. Unplanned downtime on machining cell 1

In the **final 3 weeks**, `Machining/Cell1/SpindleLoadPct` logs repeated unplanned
stoppages — spindle faults and a coolant pump failure — at roughly **20× the
preceding downtime rate** (hours per day, not hours total: a 21-day window will
always show fewer absolute hours than an 18-month one, so the rate is the only
comparison that means anything). That is a ~38% capacity loss on the cell.

The planted jobs from signal 1 are deliberately routed through `MACH-CELL1` on
tight lead times, so the two signals land on the same work — an expedite in
trouble is usually in trouble for more than one reason at once.

**Contention is the point here.** Each affected job individually fits inside the
cell's remaining hours; collectively they do not. `at_risk_jobs` therefore
allocates capacity earliest-due-date-first at each bottleneck, so a job can be
at risk because of what is queued ahead of it rather than its own size. An
earlier version assessed jobs in isolation and reported everything ON_TRACK
right up until the week they would all have been late.

The `reason_text` values are free text typed by whoever was standing there
(`spindle fault`, `SPINDLE FAULT - waiting on parts`, `spindle alarm again`),
because that is what those fields actually look like.

*Lives in:* `ignition.downtime_event` + `epicor.job_head` / `job_oper`, joined
through `xref.wc_tag`.

### 5. Remelt returns drift

`lbs_returns / lbs_charged` creeps upward across the 18 months (~9% → ~14% of
charge weight). This gives cost-per-good-casting a real trend that moves
*independently of scrap*, so the question "is our cost per good casting getting
worse, and is it scrap or is it melt?" has a genuine answer.

*Lives in:* `thrive.heat`.

| `xref.part_pattern` / `wc_tag` | 22 / 6 |

Of the 875 jobs, **44 are still open** — those drive the at-risk and scheduling
questions. Open jobs carry operations with estimates and **zero actuals** for work
the floor has not reached yet, exactly as a released Epicor job does; that is what
makes remaining-hours computable. Nothing in the dataset is timestamped after the
dataset's "today".

Historian tags are sampled every 2 hours across 9 tag paths. That is far coarser
than a real Ignition historian, which samples seconds — a deliberate tradeoff to
keep the free-tier database small and queries fast while preserving every trend
the demo depends on.

## What is *not* modeled

Stated plainly, so nobody has to discover it:

- No real costs. Labor and material rates are nominal; dollar figures are
  directionally meaningful, not accurate.
- No X-ray or radiographic data. Generating synthetic radiographs would look
  impressive to someone who has never read one and hollow to everyone at a
  foundry who reads them daily.
- No solidification modeling. LeClaire runs real simulation; faking it would be
  the same mistake.
- No BOM explosion, purchasing, or inventory.
- Only 24 parts and 12 work centers — enough for real trends, far short of a
  real plant's catalog.
- Chemistry is limited to alloy designation, degas time, and RPT density. There
  is no full spectrometer analysis.
